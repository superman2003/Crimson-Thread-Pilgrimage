## 需要打磨与验收的动作清单

以下是**尚未验收的表现任务和可选新增动作**，不是已证实的资源加载错误。没有单独命名的动画，也可能已经通过攻击姿势、位移或特效表达；应先复现，再决定是否出新图。以下建议帧数是美术排期参考，不能仅靠凑帧数验收。

- [ ] **P1：按动作时长核对姿势密度，优先检查慢前摇和长收招。** 同样 12 个姿势，播 0.3 秒约为每秒 40 次更新，播 1.2 秒只有每秒 10 次，后者更容易呈现逐格感。当前铜根主教 `boss_bishop_cage` 配置前摇 1.2 秒、收招 1.5 秒，名义更新率分别为 10、8 次/秒；百钥守门人 `boss_key_gate` 为 12/1.24≈9.68、12/1.4≈8.57 次/秒。先在相同战斗时钟下录制，再决定为这些长阶段补中间姿势；数量估算用 `目标姿势更新率 × 阶段秒数`，不要无差别翻倍全部动作。
- [ ] **P1：六位 Boss 的受击反馈。** `rust_crown_guardian`、`sunken_hammer_smith`、`silent_pilgrim_commander` 的 `hurt` 各 2 帧，`silent_crown_core` 为 3 帧；另两位为 4 帧。先核实霸体、白闪和短受击窗口的设计意图；若身体反馈不足，再补“接触受力 → 重心偏移 → 回架”姿势，不延长伤害或霸体时钟来掩盖问题。
- [ ] **P1：四种小怪的短受击段。** `spore_bellmaker`、`drain_leech`、`rust_diver`、`echo_thorn_sentinel` 的 `hurt` 各 2 帧。优先检查它们在真实命中时是否能读出受力方向，再决定是否补至 4–6 个有效姿势。
- [ ] **P1：八种小怪的短死亡段。** `gear_sentinel`、`drain_leech`、`rust_diver`、`salt_bookmite`、`erasure_bailiff`、`silent_bugbler`、`ash_banner_imp`、`echo_thorn_sentinel` 各 3 帧。逐一检查从站姿到倒地是否跳变、轮廓／武器是否连续；有问题再补失衡和落地姿势。六位 Boss 死亡均为 4 帧，也需完整退场播放验收。
- [ ] **P1：全部 40 种小怪的动作边界。** 逐行使用盘点表，检查“待机 → 移动”“移动 → 前摇”“前摇 → 出手”“出手 → 收招”“收招 → 下一动作”；精英另验 10 条专属招式。每行至少覆盖左右朝向、近身命中、挥空和受击打断；缺陷定位到具体相邻姿势后再建立补图任务。
- [ ] **P1：六位 Boss 的战斗衔接。** 每位覆盖四招、两个阶段、步态／后撤／戒备切换、连击拍间、被打断／死亡及再次进场。重点观察固定支撑脚、身体大小、武器长度、披风方向和实际位移；12 帧身体段不保证这些接点自然。
- [ ] **P2：地面角色转身与急停。** 21 种地面小怪及六位 Boss 没有独立的 `turn`／`brake` 命名片段，当前左右主要靠翻转。若试玩可见瞬间掉头或滑步，再按角色补 2–4 帧重心换边／制动接点；脚本也必须在转向或停步时选中这些动作。
- [ ] **P2：飞行角色换向和俯冲回稳。** 11 种飞行小怪已有 `walk` 飞行循环和攻击段，但没有统一独立的 `turn`／`land` 命名片段。先检查转向、俯冲退出、悬停回稳；只为确有缺口的动作补姿势，不能把 11 种都按地面步态要求重画。
- [ ] **P2：跳扑、翻越和反跳的起落连接。** 重点检查 `rust_diver`、`drain_leech`、`root_cage_hunter`，以及绯线执剪者的反跳和镜池新娘的掠袭。没有独立 `jump`／`land` 片段，但现有攻击可能已经表达起落；若缺失，补“蹬地／离地 → 空中姿态 → 接触地面／回稳”，并让实际碰撞落地触发相应姿势。
- [ ] **P2：入场、阶段切换与破防表现。** 46 个正式角色没有独立 `intro`／`stagger` 命名片段；Boss 已有 `phase` 攻击和阶段特效，不能把它们算成“没有二阶段动画”。只有策划确认需要独立表演且现有表现不足时，再补相应动作与状态机入口。
- [ ] **P3：备用二十 Boss 的玩法接入。** 将来实际增加对应战斗时，先决定沿用备用图还是重做为正式角色画风，再接招式、AI 和遭遇。不是当前六章应立刻补画二十套的任务。

8 种驻足小怪不需要为了“动作清单完整”强制新增走路、跳跃或急停。主角、NPC、地图、UI、音效不在本次逐帧覆盖范围；主分支另有 hero v9、NPC 对话 v10 等资产，不能由本次结论推断它们已经全部验收。

### 为什么不能仅凭十二帧判断丝滑

这里的十二帧是每阶段的身体姿势数，一招通常有 36 个姿势引用；与游戏每秒渲染多少画面是两个指标。现有 `_fit_animation_duration` 将动画压入招式时钟，故长阶段比短阶段更容易暴露姿势间隔。JSON 已逐招给出“帧数／配置秒数”的**名义姿势更新率**；连击会在 active 内按子节拍重播前摇和出手，不能把 active 总时长的商当成实际每拍播放率。

补更多正确的中间姿势通常能改善连续性，但不能修复比例忽大忽小、脚底滑动、动作顺序错误或接点跳变。在假定 60 fps 展示时，0.2 秒只有约 12 次画面呈现机会，塞进 24 个姿势也无法保证每个都被看见；资源和纹理开销反而会增加。若是整幅游戏画面掉帧／停顿，还需要独立的性能采样，不能由动作帧数诊断。

## 每个确认需要补图的任务应交付什么

- [ ] 记录角色 `kind`、实际 manifest、攻击 ID／动画名、缺口所在的前后帧及触发场景。
- [ ] 固定侧视、造型、比例、支撑脚／身体锚点、透明边界和完整武器；明确新姿势是替换旧帧还是增加接点。
- [ ] 更新源图来源、提示词和 manifest；新增命名动作需要实现调用入口，不能只把 PNG 放进目录。
- [ ] 对齐现有攻击／命中时钟；左右镜像、受击打断、死亡、重复进场和资源预热都要检查。
- [ ] 提供相同游戏规则、相同速度下的前后播放证据。静态拼图只证明抽样姿势可见，不替代动作连贯性验收。

## 本次检查方式与边界

实际核对了 `EnemyActor.configure` 中的“章节 → 原创战斗配置 → 遭遇覆盖 → Boss 风格 → 精英追加”选择顺序，以及 `hand_drawn_assets.gd` 的 manifest 优先级和 `_pose_sprite` 的攻击三段回退。没有把章节 JSON 的旧 sprite 路径直接当成最终资源。

除完整静态扫描外，抽看了六位 Boss 和八种小怪的待机、移动、受击、死亡、攻击关键姿势拼图，能看到不同姿势和完整角色轮廓；没有据此宣称全动画无裁切、画风一致或播放顺滑。本次未启动 Godot、未运行全部游戏回归、未验证自然带伤流程；PR 仅增加审计工具与清单。

复现冻结基线的静态检查：
