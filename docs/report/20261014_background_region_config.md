## 从参考图学习什么

参考图描述了一个 Unity 项目的全局管理、角色控制、玩家数据、房间异步加载、音频混音和对象池。具体插件数量和代码行数仅来自用户提供的图片，未经源码核实。本项目使用 Godot；参考的价值在职责与生命周期管理。

| 优先级 | 借鉴原则 | 项目下一步 |
|---|---|---|
| 本批 | 异步读取，完成后激活 | 将冷缓存目标配置读取/JSON解析移出主线程；沿用现有分帧校验与区域交接 |
| 下一批 | 房间提前准备 | 邻区配置读取和验证仍同步；引入有界后台读取与增量验证，再预算化路线覆盖/缓存复制 |
| 后续 | 角色动作独立管理 | 按输入缓冲、动作状态、移动/战斗职责梳理Player；以行为回归为拆分边界 |
| 后续 | 玩家数据独立管理 | 先核查现有存档迁移、备份恢复和数据结构，补齐故障用例；不为模仿而加入AES |
| 后续 | 音频和短命对象有独立生命周期 | 以已有退休/驻留服务为基础，测量高频特效分配，再决定复用范围与音频层切换 |

Godot官方说明：活动SceneTree不能从工作线程任意操作；Thread完成后需要join。这里让工作线程只拥有FileAccess、JSON及其返回值，主线程接收后才进入验证和场景装载。参考：[线程安全API](https://docs.godotengine.org/en/4.6/tutorials/performance/thread_safe_apis.html)、[Thread](https://docs.godotengine.org/en/4.6/classes/class_thread.html)。

## 最终行为

新增 `WorldConfigReadJob` 服务，每个持久区域loader至多持有一个工作线程和一个未接收结果。工作线程读取文件并解析独立JSON对象，不访问World、玩家、共享缓存、路线配置或SceneTree。结果通过已完成线程的 `wait_to_finish` 交回；普通轮询只在 `is_alive == false` 后join，没有同步读取回退。

`replace_region_async` 的缓存未命中路径逐帧等待，并至少让出一帧供取消输入。收到结果后，现有校验器仍每帧最多准入8步、2ms后停止准入下一步，通过校验后才保存/交接来源区。缓存命中沿用现有深拷贝及验证语义。

取消立即废弃票据并返回来源区；文件读取本身不能强制中断。尚未完成的旧任务最多保留一个，直到下一次request或宿主退出回收；新request分帧等待旧任务结束再启动，旧票据无法取回或发布目的区。整段旅途退出可以等待尚未结束的线程，这属于teardown，不是普通切区帧预算。后台启动失败和读取失败保留来源区并显示错误，不在主线程重做读取。

指标 `json_background`、`json_wait_frames`、`json_worker_is_main`、`json_worker_usec`、`json_bytes` 区分后台任务、等待帧数和实际工作；原 `preflight_json_usec` 现在是前置读取/缓存阶段墙钟时间，冷缓存路径含逐帧等待，不能解释为主线程CPU开销。`preflight_wall_usec`仍包括这一阶段。文件mtime检查是尽力检测读取期间变化，其时间戳精度不保证捕获同秒改写。
