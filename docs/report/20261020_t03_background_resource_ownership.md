# T03：后台资源读取的明确所有权

上一轮固定 b04a1b09 的 30 分钟测量在退出时留下 15 个零引用 RefCounted，仍然失败，记录保留在 [草稿 #168](https://github.com/superman2003/Crimson-Thread-Pilgrimage/pull/168)。本批追查角色图集预热及相邻区域纹理预取，不调整泄漏判定或帧预算。

先将纯 JSON 读取和完整区域校验连续执行 60 次，没有退出泄漏。再用独立空项目、同一 Godot 4.6.1 二进制、100 次真实 Resource 读取复现：内建 load_threaded_request/get 留下 100 个零引用 RefCounted 和 99 个 Resource；改为显式 Thread 内调用 ResourceLoader.load，再在主线程回收 Thread，100 次全部取得正确数据，退出零泄漏。这证明目标引擎该接口可独立产生同类问题；具体 C++ 令牌销毁位置仍属于结合[上游问题 #120661](https://github.com/godotengine/godot/issues/120661)的推断，没有对本机二进制加调试日志。

新增 background_resource_job，由调用者持有单个后台 Thread 和未领取结果。主线程只能在 ready 后正常 take；普通取消保留所有者，完成后按原租约丢弃陈旧结果；整宿主退出才允许等待剩余读取。角色共享图集队列与相邻地区队列均改用该对象，原每队列最多两个、每帧操作/时间准入上限、路径去重和区域代际/文件时间检查保留。宿主退出也回收共享图集请求，将成功解码的不可变图集保留给共享缓存的其它宿主。

当前运行时只在线程中预读导入图片。开发测试曾把程序纹理 GradientTexture2D 写成 .tres，再立即退出，导致工作线程等待主渲染线程而主线程等待工作线程：原生 GL 调试在 20 秒终止，初轮 QA 预热在原 180 秒上限超时。该失败原样保留；现在 Texture2D 请求在启动线程前拒绝 .tres/.res，避免把这类资源引入现有图集通道。真实导入 PNG 连续 100 次启动后立即 shutdown，均完成且没有泄漏；共享图集测试覆盖两请求上限、第三项等待、带实际请求的计划取消、退出回收与供其它宿主使用的缓存结果。
